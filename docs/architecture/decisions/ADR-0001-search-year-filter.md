# ADR-0001: Учёт года при поиске метаданных после миграции на API v1.5

## Статус

Accepted (в рамках фичи `api-v1-5-upgrade`; решено с Стейхолдером 2026-08-23)

## Контекст

Плагин при поиске метаданных передаёт год (например, из формы «Распознать»/Identify в Jellyfin) как query-параметр `year` к `GET /v1.4/movie/search`. Выяснилось:

- В спецификации `movie/search` параметр `year` **не документирован ни в v1.4, ни в v1.5** — там только `page`/`limit`/`query`. Параметр всегда был недокументированным, и гарантий его серверной обработки нет.
- Документированный фильтр `year` есть только у универсального `GET /v1.5/movie` (синтаксис `2020`, `!2020`, `2020-2024`), но это листинг с курсорной пагинацией — другая семантика и контракт.
- Элементы ответа поиска содержат поле `year` (`SearchMovieDtoV1_4.year`; для сериалов — диапазон `releaseYears`), то есть фильтрацию можно выполнить на стороне плагина.

Бизнес-требование: год, указанный пользователем в Identify, должен детерминированно влиять на релевантность результатов поиска метаданных.

## Решение

Гибридный вариант A с сохранением текущего поведения:

1. При миграции на `GET /v1.5/movie/search` **сохранить передачу** недокументированного `&year=` в URL — если сервер его учитывает (как предположительно в v1.4), поведение не деградирует.
2. Добавить **локальную фильтрацию результатов по году в провайдерах** (слой приложения): точное совпадение `item.Year` для фильмов; попадание года в `releaseYears` (или совпадение с `Year`) для сериалов. Если после фильтрации пусто, а до неё были результаты — вернуть неотфильтрованный список с debug-log (защита полноты). Год не указан — фильтрация не применяется.
3. Фильтрация размещается в провайдерах, не в `PoiskKinoApiClient`: клиент остаётся транспортным адаптером без бизнес-правил (clean architecture). Кэш хранит сырой ответ API.

## Последствия

**Плюсы**

- Гарантированное бизнес-поведение «поиск с учётом года» независимо от сервера.
- Минимальная дельта миграции: два URL + локальный предикат; эндпоинт и контракт ответа не меняются.
- Изолированная деградация: если v1.5 отклонит неизвестный `year=`, достаточно убрать одну строку конкатенации URL — локальная фильтрация уже покрывает требование.

**Минусы / риски**

- Если сервер игнорирует `year`, топ-N (limit=3) серверной выдачи может не содержать совпадений по году → срабатывает fallback без фильтра (полнота сохранена, точность — как раньше). При необходимости можно поднять `limit`, но это отдельное решение (сейчас вне scope).
- Логика фильтрации требует собственных юнит-тестов.

**Влияние на операции:** smoke-тест после реализации — запрос `/v1.5/movie/search?...&year=` с реальным ключом обязан вернуть 200; иначе применить план изоляции отказа (убрать параметр).

## Альтернативы

- **B. Перейти на универсальный `GET /v1.5/movie`** с документированными фильтрами `name`/`year`: отвергнуто — другая семантика (листинг vs текстовый поиск), курсорная пагинация, лимиты demo/free (10 страниц), существенно больший объём изменений ради эквивалентного результата; выход за scope фичи (analysis.md §10).
- **C. Убрать `year` полностью**, положившись только на серверный поиск по названию: отвергнуто — нарушает бизнес-требование Стейхолдера об учёте года в Identify.
