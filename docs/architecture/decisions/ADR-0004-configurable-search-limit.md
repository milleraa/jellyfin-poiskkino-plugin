# ADR-0004: Настраиваемый лимит результатов поиска

## Статус

Accepted (в рамках фичи `search-limit-setting`; решения Стейхолдера по Q1/Q2 зафиксированы 2026-11-28 в [status.md](../../archive/features/search-limit-setting/status.md))

## Контекст

`PoiskKinoApiClient.SearchAsync` строит URL с жёстко заданным `&limit=3` (`PoiskKinoApiClient.cs:105`). Администратор не может получить больше подсказок в identify-диалоге Jellyfin. Ключ кэша поиска `search:{title}[:{year}]` (`PoiskKinoApiClient.cs:481-484`) лимита не учитывает: при выносе лимита в настройку повторный поиск после её смены вернул бы закэшированную выдачу со старым лимитом (TTL 24 ч, негативный кэш 1 ч).

Решения Стейхолдера (фиксированные ограничения):

- **Q1:** диапазон настройки **1–10**, значение по умолчанию **3**.
- **Q2:** **вариант А** — лимит включается в ключ кэша поиска.

Требование применения настройки **без перезапуска** Jellyfin — приоритет над паттерном `ApiBaseUrl` (фиксируется при создании клиента в `Lazy<>`, смена требует перезапуска; ADR-0003). Эталон поведения — паттерн `ApiKey`: чтение из `Plugin.Instance.Configuration` на каждый вызов (`PoiskKinoMovieProvider.cs:32`).

## Решение

1. **Проброс параметром, не чтение конфигурации клиентом.** `SearchAsync` получает новый параметр `int searchLimit = 3` (необязательный — существующие вызовы и тесты совместимы). Провайдеры (Movie, Series, Image — все три вызова `SearchAsync`: `PoiskKinoMovieProvider.cs:79`, `PoiskKinoSeriesProvider.cs:79`, `PoiskKinoImageProvider.cs:95`) читают `Plugin.Instance?.Configuration?.SearchLimit` на каждый вызов свойством-выражением по образцу `ApiKey` и передают параметром. Клиент остаётся транспортным адаптером без ссылок на `Plugin` (направление зависимости — внутрь; ADR-0001, принципы clean architecture). Фиксация лимита в конструкторе клиента отвергнута: клиент создаётся в `Lazy<>` один раз на провайдера — смена требовала бы перезапуска (как `ApiBaseUrl`, ADR-0003).
2. **Валидация — единая серверная точка в клиенте.** UI (`type="number" min="1" max="10"`) — только UX, не доверяем (D-ARCH-4). В `SearchAsync` сырое значение нормализуется чистой функцией без исключений: значение в диапазоне 1–10 применяется как есть; вне диапазона, неположительное — дефолт `3` + `Warning` (по AC-4 — fallback на дефолт, а не clamping). Рекомендуемая форма — внутренний статический резолвер по образцу `ApiBaseUrlResolver` (единственная точка политики, тестируемость); допустима inline-проверка. `Warning` не должен спамить на каждый поиск (механизм дедупликации — решение Техлида).
3. **Раскладка ключа кэша (вариант А).** Ключ дополнен **эффективным** (после валидации) лимитом: `search:{normalizedTitle}[:{year}]:{limit}`. Лимит всегда присутствует в ключе (без условного опускания при дефолте — «явное лучше неявного»). URL (`limit=N`) и ключ (`:N`) строятся из одного разрешённого значения — детерминированная пара «запрос ⇔ запись кэша». Записи старого формата становятся недостижимыми и истекают естественно (TTL 24 ч; кэш in-memory и стирается при перезапуске) — миграция не нужна.

## Последствия

**Плюсы**

- Настройка применяется к следующему некэшированному поиску без перезапуска (AC-7).
- Записи кэша с разными лимитами не смешиваются; смена настройки видна сразу (AC-5).
- Клиент тестируется существующим Moq-контуром без `Plugin.Instance`; необязательный параметр сохраняет смысл текущих тестов (`SearchAsync_CachesResult`, `SearchAsync_NotFound_CachesNegativeResult`).
- Память кэша растёт пренебрежимо: ≤10 различных ключей на один запрос.

**Минусы / риски**

- Возможный рост числа записей кэша при частых сменах лимита — ограничено диапазоном 1–10, незначимо.
- `Warning` при невалидном сохранённом значении может повторяться при каждом поиске — требуется дедупликация лога.
- Разбор ключа неоднозначен, если название содержит `:` — риск существующий (ключ никогда не парсится, используется только для точного lookup), не усугубляется.

**Влияние на операции:** без влияния на окружения, секреты, CI и упаковку (новых env/secrets/шагов нет). Поведенческое изменение — формат ключа кэша — прозрачно для пользователя.

## Альтернативы

- **Клиент читает `Plugin.Instance.Configuration` сам:** отвергнуто — связывает транспортный адаптер со статическим состоянием хоста плагина, ломает сложившуюся сигнатурную передачу (`apiKey` параметром), усложняет юнит-тесты клиента.
- **Лимит фиксируется в конструкторе клиента:** отвергнуто — смена настройки требует перезапуска Jellyfin (AC-7), деградация UX по сравнению с паттерном `ApiKey`.
- **Вариант Б (лимит вне ключа кэша, документированное устаревание до TTL):** отвергнут Стейхолдером (Q2, 2026-11-28) — сценарий «сменил и сразу повторил поиск» выглядел бы неработающим до 24 ч (R2).
- **Clamping значения в границы 1–10** (например, 15 → 10): отвергнуто — AC-4 требует детерминированный fallback на дефолт с `Warning`; silent-исправление скрывает ошибку администратора.
