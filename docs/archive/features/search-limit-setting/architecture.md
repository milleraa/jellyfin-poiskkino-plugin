# Architecture — `search-limit-setting`

Дата: 2026-11-28. Автор: Архитектор. Статус: дизайн готов → `tech-decomposition`.

## Контекст

Ссылки на глобальный обзор: [architecture overview](../../../architecture/overview.md), принципы: [principles](../../../architecture/principles.md).

Фактура и AC: [analysis.md](analysis.md) (F1–F13, AC-1…AC-10, D-1…D-5). Фиксированные ограничения Стейхолдера (status.md, 2026-11-28):

- **Q1:** диапазон лимита **1–10**, дефолт **3**.
- **Q2:** кэш — **вариант А**, лимит в ключе кэша поиска.

Целевой объект — `PoiskKinoApiClient.SearchAsync` (`PoiskKinoMetadataPlugin/PoiskKinoApiClient.cs:73-77`, хардкод `limit=3` на `:105`); потребители — три вызова: `PoiskKinoMovieProvider.cs:79`, `PoiskKinoSeriesProvider.cs:79`, `PoiskKinoImageProvider.cs:95` (проверено grep по `SearchAsync`); ключ кэша — `GenerateCacheKey` (`:481-484`); конфигурация — `Configuration.cs` (`ApiKey`, `ApiBaseUrl`, `IgnoreTmdbImages`); UI — `Configuration/configPage.html`.

## Решение: как настройка попадает в `SearchAsync`

Сравнение вариантов:

| Вариант | Суть | Оценка |
|---------|------|--------|
| **1. Проброс параметром (выбран)** | Провайдеры читают `Plugin.Instance?.Configuration?.SearchLimit` на каждый вызов (паттерн `ApiKey`) и передают параметром `int searchLimit = 3` в `SearchAsync` | Клиент остаётся транспортным адаптером без ссылок на `Plugin` (DIP, как `apiKey` сегодня); тесты клиента через Moq-обработчик без хоста; применяется без перезапуска; необязательный параметр сохраняет совместимость существующих тестов |
| 2. Клиент читает конфигурацию сам | `SearchAsync` внутри обращается к `Plugin.Instance.Configuration` | Связывает инфраструктурный адаптер со статическим состоянием хоста (зависимость наружу), усложняет юнит-тесты, ломает сложившуюся сигнатурную передачу (`apiKey` параметром) |
| 3. Лимит фиксируется в конструкторе клиента | Третий параметр конструктора, как `apiBaseUrl` | Клиент создаётся в `Lazy<>` один раз на провайдера — смена настройки требует перезапуска Jellyfin (поведение `ApiBaseUrl`, ADR-0003); нарушает требование AC-7 «без перезапуска» |

**Выбран вариант 1** — приоритет паттерну `ApiKey` (чтение на каждый вызов, применение без перезапуска), зависимость направлена внутрь. Каждому из трёх провайдеров добавляется свойство-выражение `SearchLimit` по образцу `ApiKey` (`PoiskKinoMovieProvider.cs:32`); точка вызова у каждого одна, включая fallback-путь `GetMetadataInternal → GetSearchResultsInternal` в провайдерах фильмов/сериалов.

## Валидация диапазона: точка

Единая авторитетная точка — **в клиенте**, перед построением URL и ключа кэша:

1. **UI** (`configPage.html`): `type="number" min="1" max="10"` + русская подсказка (назначение, диапазон, применение сразу) — только UX, **не доверяем** (D-ARCH-4).
2. **Провайдеры**: сырое пробрасывание без валидации — как `ApiKey`.
3. **Клиент `SearchAsync`**: чистая функция без исключений — значение в 1–10 применяется как есть; вне диапазона/неположительное — дефолт `3` + `Warning` (без утечки ключа; дедупликация лога — решение Техлида). Повреждённый XML исключений не добавляет (AC-4, R5). Рекомендуемая форма — внутренний статический резолвер по образцу `ApiBaseUrlResolver` (единственная точка политики, ADR-0003); допустима inline-проверка.

## Раскладка ключа кэша (вариант А)

```text
было:  search:{normalizedTitle}[:{year}]
стало: search:{normalizedTitle}[:{year}]:{limit}
```

- `{limit}` — **эффективное** (после валидации) значение, то же, что уходит в URL `limit=N`: пара «запрос ⇔ ключ» детерминирована; невалидное сырое значение не порождает мусорных ключей.
- Лимит присутствует в ключе всегда, без условного опускания при дефолте («явное лучше неявного»).
- Ключи никогда не парсятся (только точный lookup в `ConcurrentDictionary`) — неоднозначность при `:` в названии существовала и раньше, не усугубляется.
- Записи старого формата становятся недостижимыми и истекают естественно (TTL 24 ч, негативный 1 ч; кэш in-memory, стирается при перезапуске — F6, F3) — миграции нет.
- Память: ≤10 разных ключей на один запрос — незначимо. TTL, негативный кэш, rate-limit 200/сутки, таймауты не меняются (D-5, AC-9).

## Потоки данных

```text
[configPage.html] --сохранение--> PluginConfiguration.SearchLimit (int, дефолт 3, XML Jellyfin)
     ↓ (UI: number 1..10 — только UX)
Provider (Movie/Series/Image) --каждый вызов--> SearchLimit = Plugin.Instance?.Configuration?.SearchLimit (паттерн ApiKey)
     ↓ параметр
PoiskKinoApiClient.SearchAsync(title, year, apiKey, searchLimit, ct)
     ├─ валидация 1..10 → эффективный limit (fallback 3 + Warning)
     ├─ ключ = search:{title}[:{year}]:{limit}  → кэш-хит → ответ без запроса
     └─ промах → GET /v1.5/movie/search?query=…&limit={limit}[&year=…] → кэширование по ключу
```

## Компоненты и границы

| Компонент | Изменение | Граница |
|-----------|-----------|---------|
| `Configuration.cs` | +`int SearchLimit { get; set; } = 3`; имя свойства — часть XML-схемы (как `ApiBaseUrl`, ADR-0003) | домен конфигурации Jellyfin |
| Провайдеры (Movie, Series, Image) | +свойство `SearchLimit` (паттерн `ApiKey`), +аргумент в единственный вызов `SearchAsync` | слой приложения; бизнес-фильтры (тип, `SearchYearFilter`) не меняются |
| `PoiskKinoApiClient` | +параметр `int searchLimit = 3`; +валидация (fallback/Warning); `GenerateCacheKey` +лимит; URL `limit={limit}` вместо хардкода | транспортный адаптер, ссылок на `Plugin` не появляется |
| `Configuration/configPage.html` | +числовое поле `min=1 max=10` с подсказкой на русском | UI настроек Dashboard |
| README.md | +описание поля: дефолт 3, диапазон 1–10, применение без перезапуска (AC-10, F13) | документация |

Изменений нет: контракт API `/v1.5/movie/search` (кроме значения `limit`), пагинация (out of scope), `SearchYearFilter` (ADR-0001), TTL/ rate-limit, DevOps-контур (env/secrets/CI).

## Влияние на тесты и модель кэша

**Существующие тесты** (`PoiskKinoMetadataPlugin.UnitTests/ApiClient/PoiskKinoApiClientTests.cs`): необязательный параметр `searchLimit = 3` сохраняет компиляцию и смысл — `SearchAsync_WithYear_IncludesYearInUrl`, `SearchAsync_Success_RequestsV15SearchPath` (URL с `limit=3` идентичен текущему, AC-3), `SearchAsync_CachesResult` / `SearchAsync_NotFound_CachesNegativeResult` (одинаковый лимит → тот же ключ). Фикстура `PluginTestFixture` (`Activator.CreateInstance`, F11) покрывает дефолт конфигурации.

**Новые тесты:** дефолт пустой/старой XML-конфигурации → 3 (AC-1); URL с настроенным лимитом `limit=N` через захват `HttpRequestMessage.RequestUri` (AC-2, контур `CreateCapturingHandlerMock`); таблица валидации (0, −1, 11, границы 1/10) + лог-ассерт (AC-4); разделение кэша: тот же title, другой лимит → второй сетевой запрос; тот же лимит → кэш-хит (AC-5); чтение лимита из конфигурации на каждый вызов (AC-7).

**ADR нужен:** решение меняет формат ключа кэша (раскладка данных) и закрепляет выбор направления зависимости с отвергнутой альтернативой; прецедент масштаба — ADR-0001. Тривиальным решение не является из-за взаимодействия «настройка ⇔ кэш», поэтому обоснование вынесено в ADR-0004, а не только в этот документ.

## Риски

| # | Риск | Митигация |
|---|------|-----------|
| A1 | Повторный `Warning` при каждом поиске с невалидно сохранённым значением — спам в логе | Дедупликация (один `Warning` до изменения конфигурации) — решение Техлида на tech-decomposition |
| A2 | Устаревшие записи кэша старого формата занимают память до 24 ч | Приемлемо: in-memory, ≤24 ч, стираются при перезапуске; наблюдаемой деградации нет |
| A3 | Два ключа (старый/новый) во время перехода дают «двойной» промах кэша на один запрос | Однократно, ≤24 ч; самоустраняется истечением |
| A4 | Поведение demo-тарифа при `limit > 10` недокументировано (R1 анализа) | Снято диапазоном 1–10 (решение Q1) |
| A5 | Мусор из UI (нечисловое) в URL | UI `type="number"` + серверная валидация с fallback (AC-4); нечисловой XML Jellyfin пересоздаёт конфиг (существующее поведение, R5) |
