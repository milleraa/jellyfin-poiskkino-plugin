# Analysis — `search-limit-setting`

Дата: 2026-11-28. Автор: Аналитик. Источники: код плагина (`PoiskKinoMetadataPlugin/`), снимок спеки `api-docs/documentation.yaml` (обновлён 2026-11-27), [llms.txt](https://api.poiskkino.dev/llms.txt), существующие юнит-тесты. Код в рамках анализа не изменялся.

## Резюме

Лимит выдачи поиска жёстко задан в URL запроса: `PoiskKinoApiClient.cs:105` строит `/v1.5/movie/search?query=...&limit=3` (опционально `&year=`). Сигнатура `SearchAsync(title, year, apiKey, ct)` лимита не содержит; клиент используется тремя провайдерами (фильмы, сериалы, изображения) через один и тот же вызов. Задача сводится к: (1) целочисленное поле `SearchLimit` в `PluginConfiguration` с дефолтом `3`, (2) валидация диапазона с безопасным fallback на дефолт, (3) проброс значения в `SearchAsync` вместо хардкода, (4) числовое поле в `Configuration/configPage.html`, (5) юнит-тесты и документация. Контракт API не меняется: спека `/v1.5/movie/search` описывает `limit` как `minimum: 1, maximum: 250, default: 10` (`documentation.yaml:974-982`).

Ключевой технический риск — кэш: ключ поиска строится без учёта лимита (`search:{title}:{year}`, `PoiskKinoApiClient.cs:481-484`), TTL — 24 часа (`CacheExpirationHours = 24`, `:15`), отрицательный результат — 1 час (`:136`). Без решения по кэшу смена настройки будет выглядеть неработающей: при повторном поиске пользователь получит закэшированную выдачу со старым лимитом. Рекомендация — включить лимит в ключ кэша (вопрос Q2, решение D-4).

## 2. User stories

1. **Как администратор Jellyfin**, я хочу задать количество результатов поиска ПоискКино в настройках плагина, чтобы при ручной идентификации фильма/сериала получать больше подсказок и находить тайтл, который не попадал в выдачу из трёх результатов.
2. **Как администратор, который не менял настройку**, я хочу, чтобы после обновления плагина поведение поиска не изменилось (дефолт `3` = текущее поведение, конфигурация не сбрасывается).
3. **Как администратор, изменивший настройку**, я хочу предсказуемое применение нового значения к последующим поискам и понятное поведение кэша, чтобы не считать настройку «сломанной».
4. **Как администратор, ошибочно введший значение вне допустимого диапазона**, я хочу, чтобы плагин не падал, а применял безопасное значение по умолчанию с понятной подсказкой в UI.
5. **Как QA/разработчик**, я хочу юнит-тесты на дефолт, валидацию, проброс лимита в URL и поведение кэша, чтобы регрессия «снова жёсткий `limit=3`» ловилась CI.

## 3. Acceptance criteria

Проверяемые; в скобках — способ проверки. Финальная верхняя граница диапазона — по решению Q1 (ниже — ориентир 1–10).

**AC-1. Поле конфигурации с дефолтом.** `PluginConfiguration` содержит целочисленное свойство количества результатов поиска (`SearchLimit`, имя финализирует Архитектор) с дефолтом `3`; XML-конфигурация без этого элемента даёт именно дефолт, старые `ApiKey`/`ApiBaseUrl`/`IgnoreTmdbImages` не сбрасываются. *(unit-тест на дефолт пустой/старой конфигурации — паттерн F11)*

**AC-2. Проброс во все поиски.** `SearchAsync` строит URL с настроенным лимитом вместо хардкода `3`; все три потребителя (провайдеры фильмов, сериалов, изображений) идут через один механизм. *(unit-тест: захват `HttpRequestMessage.RequestUri`, проверка `limit=N`)*

**AC-3. Дефолт сохраняет текущее поведение.** При значении по умолчанию запрос идентичен текущему: `/v1.5/movie/search?query=...&limit=3[&year=...]`. *(unit-тест)*

**AC-4. Валидация диапазона без падения.** Значение валидируется детерминированно на стороне плагина: значение в диапазоне (ориентир 1–10) применяется как есть; вне диапазона, неположительное или нечисловое — используется дефолт `3` и пишется `Warning` в лог один раз (без утечки API-ключа), исключения не выбрасываются. Повреждённый XML-конфиг с нечисловым значением не должен приводить к новому классу ошибок (существующее поведение Jellyfin — пересоздание дефолтной конфигурации — сохраняется). *(unit-тесты таблицей кейсов + лог-ассерт)*

**AC-5. Кэш (по решению Q2).** Вариант А (рекомендация): лимит входит в ключ кэша поиска, смена настройки влияет на следующий некэшированный поиск сразу; записи с разными лимитами не смешиваются. Вариант Б: лимит в ключ не входит, поведение «смена действует после истечения кэша (до 24 ч) или перезапуска Jellyfin» явно задокументировано в README и подсказке UI. В обоих вариантах существующие тесты `SearchAsync_CachesResult` / `SearchAsync_NotFound_CachesNegativeResult` сохраняют смысл и расширяются на новый случай. *(unit-тесты)*

**AC-6. UI.** В `configPage.html` есть числовое поле (`type="number"` с `min`/`max`), которое загружает сохранённое значение (при отсутствии — `3`), сохраняется вместе с остальными настройками и содержит подсказку на русском (что делает, допустимый диапазон, поведение применения — по AC-5). *(ручная проверка UI Jellyfin: сохранить → перезагрузить страницу → значение на месте)*

**AC-7. Применение к новым поискам без перезапуска.** Значение читается из конфигурации при каждом вызове поиска (паттерн `ApiKey`, F5), а не фиксируется при создании клиента: после сохранения настройки следующий поиск вне кэша уходит с новым лимитом без перезапуска Jellyfin. *(unit-тест на чтение значения из конфигурации + smoke в живом Jellyfin)*

**AC-8. Персистентность.** Значение переживает перезапуск Jellyfin и сохраняется в существующем XML-файле конфигурации. *(smoke: сохранить, перезапустить, проверить UI и файл конфигурации)*

**AC-9. Нагрузка на лимиты тарифа не растёт.** Увеличение `limit` не увеличивает число запросов к API (одна страница поиска), т.е. клиентский лимит 200 запросов/сутки (F12) и условия demo-тарифа не затрагиваются. *(код-ревью: изменений в подсчёте запросов нет)*

**AC-10. Тесты, сборка, документация.** Добавлены unit-тесты на AC-1/AC-2/AC-3/AC-4/AC-5; полный прогон `dotnet test` зелёный; `dotnet build -c Release` без новых предупреждений; README (перечень настроек, раздел «Настройка») описывает новое поле с дефолтом и диапазоном (F13). *(CI/локальный прогон, code review docs)*

## 4. NFR

| NFR | Требование |

| Бизнес-ограничения | Спека допускает `limit` до 250, но для identify-диалога Jellyfin больший объём не имеет практической ценности (см. Q1) |

## 6. Открытые вопросы (Стейхолдеру)

1. **Q1. Дефолт и верхняя граница диапазона.** Рекомендация: диапазон **1–10**, дефолт **3**. Дефолт сохраняет текущее поведение; верхняя граница 10 безопасна при любой трактовке demo-лимитов (R1) и достаточна для identify-диалога. Спека допускает до 250 — если Стейхолдеру нужна большая выдача, границу можно поднять, но тогда желателен smoke с реальным demo-ключом.
2. **Q2. Поведение кэша при смене настройки.** Рекомендация: **вариант А — лимит входит в ключ кэша** (`search:{title}:{year}` → с лимитом; раскладку ключа финализирует Архитектор). Аргументы: ключевой сценарий пользователя — «сменил настройку и сразу повторил поиск»; без учёта лимита он получит старую выдачу (до 24 ч, негативный кэш — до 1 ч) и решит, что настройка не работает (R2); стоимость минимальна — `GenerateCacheKey` уже принимает title/year. Вариант Б (осознанное устаревание кэша до истечения TTL/перезапуска) допустим при явной приписке в README и подсказке UI (AC-5, вариант Б).

Блокирующих вопросов нет: по обоим есть рекомендация, они не мешают Архитектору начать работу.

## 7. Решения (для Архитектора и Техлида)

- **D-1.** Дефолт `3` — сохранение текущего поведения; миграция конфигурации не нужна (AC-1).
- **D-2.** Лимит передаётся в `SearchAsync` параметром на каждый вызов и читается из конфигурации при вызове (паттерн `ApiKey`), а не фиксируется в конструкторе клиента — иначе смена потребовала бы перезапуска, как `ApiBaseUrl` (F5, AC-7).
- **D-3.** Валидация — единая серверная точка с fallback на дефолт и `Warning` (паттерн `ApiBaseUrlResolver`/D-ARCH-4); UI не доверяем (AC-4).
- **D-4.** Целевое решение по кэшу — вариант А (лимит в ключе, Q2); при выборе Стейхолдером варианта Б — обязательная документация в README и подсказке UI.
- **D-5.** Существующие кэш-TTL (24 ч / 1 ч негативный), клиентский rate-limit 200/сутки, таймауты и обработка ошибок не меняются (AC-9).

## 8. Out of scope

- Пагинация и повторные запросы за пределами первой страницы результатов (подтверждаю brief).
- Изменение эндпоинта `/v1.5/movie/search` и его параметров кроме `limit` (включая недокументированный `year`).
- Настройки фильтрации по году (`SearchYearFilter`, ADR-0001) и локальная фильтрация типов контента в провайдерах.
- Per-provider (фильмы/сериалы/изображения) или per-library лимиты.
- Автоматическая очистка/инвалидация кэша при смене настройки за пределами решения Q2.
