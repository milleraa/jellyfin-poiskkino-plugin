# Analysis — `logo-images`

Дата анализа: 2026-08-24. Все гипотезы брифа проверены по коду (`PoiskKinoMetadataPlugin/`) и OpenAPI-спеке (`api-docs/documentation.yaml`).

## Проверенные факты (evidence)

| Гипотеза брифа | Результат | Evidence |
|----------------|-----------|----------|
| Поле `Logo` доступно в детальных данных `/v1.5/movie/{id}` | ✅ Подтверждено | `Models/PoiskKinoMovieDto.cs:254` (`[JsonPropertyName("logo")]`); схема `MovieDtoV1_4`, эндпоинт «Возвращает всю доступную информацию о сущности» (documentation.yaml:2416–2435) |
| Поле `Logo` декларировано в модели поиска | ✅ Подтверждено | `Models/PoiskKinoItem.cs:134`; схема `SearchMovieDtoV1_4` содержит `logo` типа `Logo` (documentation.yaml:8918–8921) |
| `logo` есть в дефолтных полях ответа поиска `/v1.5/movie/search` | ✅ **Да** | Эндпоинт поиска вообще **не имеет** параметра `selectFields` (documentation.yaml:2472–2507) — сервер отдаёт фиксированный набор полей схемы `SearchMovieDtoV1_4`, в который `logo` входит. Условие out-of-scope из брифа («если API не отдаёт logo») **не выполняется**: поле приходит всегда, когда оно заполнено у тайтла |
| Схема `Logo` в API | Только `url` (nullable), без `previewUrl` (documentation.yaml:8264–8270) | Модель плагина `PoiskKinoImage` содержит и `Url`, и `PreviewUrl`; для логотипа используется только `Url` |
| Провайдер ищет по ID, затем fallback на поиск | ✅ Подтверждено | `PoiskKinoImageProvider.cs:65–125`: ProviderId → `GetMovieByIdAsync`; иначе поиск → выбор кандидата → снова `GetMovieByIdAsync`; если полные данные недоступны — постер/фон из результата поиска |
| Фильтрация TMDB применяется к логотипам | ✅ Автоматически, но не через `ShouldFilterUrl` | В `GetImages` фильтр реализован как пост-обработка всего списка: `ImageUrlHelper.ShouldIgnoreTmdbImages()` + `IsTmdbUrl(img.Url)` (PoiskKinoImageProvider.cs:189–197). Любое изображение, добавленное в список с URL на `tmdb.org`, отфильтруется. `ShouldFilterUrl` используется в metadata-провайдерах (Movie/Series/Season/Episode), но не в image-провайдере — для логотипов достаточно существующего пост-фильтра |

Корректировка брифа: формулировка «применять `ShouldFilterUrl` к логотипам» уточнена — в `PoiskKinoImageProvider` действует эквивалентный пост-фильтр TMDB поверх итогового списка; отдельный вызов `ShouldFilterUrl` при добавлении логотипа не нужен (но допустим как защитная проверка — решение за Архитектором).

## User stories

1. **US-1**: Как пользователь Jellyfin, я хочу видеть логотип тайтла из ПоискКино на карточках и экранах деталей (веб/TV-клиенты), чтобы оформление соответствовало фирменному стилю тайтла.
2. **US-2**: Как администратор сервера, я хочу, чтобы логотипы подчинялись той же настройке «игнорировать изображения TMDB», что и постеры/фоны, чтобы политика источников изображений была единой.

## Acceptance criteria

### Функциональные

1. `PoiskKinoImageProvider.GetSupportedImages` возвращает `[Primary, Backdrop, Logo]`.
2. При получении полных данных по ID (`GetMovieByIdAsync`) провайдер добавляет `RemoteImageInfo { Url = movieData.Logo.Url, Type = ImageType.Logo }`, если `movieData.Logo?.Url` непустая строка.
3. Логотип не добавляется, если `movieData.Logo` равен `null` или `movieData.Logo.Url` пустой/состоит из пробелов — ответ просто не содержит изображений типа `Logo` (без ошибок).
4. Существующее поведение для `Primary`/`Backdrop` не меняется.
5. Типы `Supports` (Movie/Series/Season) не меняются; логотип доступен для всех поддерживаемых типов, у которых есть PoiskKino ID.

### Фильтрация

6. При включённой настройке `IgnoreTmdbImages` логотип с URL домена `tmdb.org` не возвращается (покрывается существующим пост-фильтром `IsTmdbUrl`); логотип с другим доменом возвращается.
7. При выключенной настройке `IgnoreTmdbImages` логотип с любым URL возвращается как есть.

### Тесты

8. Unit-тест обновлён: `GetSupportedImages_ReturnsPrimaryAndBackdrop` → ожидается 3 типа, включая `ImageType.Logo`.
9. Unit-тест обновлён: `GetImages_ByProviderId_ReturnsPosterAndBackdrop` → тестовые данные `FullMovieDtoJson` уже содержат `logo.url` (`oppenheimer-logo.png`, TestData/TestJsonData.cs:54–57), поэтому ожидается 3 изображения, включая `ImageType.Logo`.
10. Новый unit-тест: логотип отсутствует в ответе API (`"logo": null` или поле отсутствует) → в результате нет изображений `Logo`, ошибок нет.
11. Новый unit-тест: логотип с TMDB-URL при включённом `IgnoreTmdbImages` отфильтрован, остальные изображения остаются.
12. Весь существующий набор unit-тестов зелёный (`dotnet test`).

### Edge cases

| Кейс | Ожидаемое поведение |
|------|---------------------|
| `Logo == null` (у тайтла нет логотипа) | Нет изображения `Logo`; AC-3 |
| `Logo.Url` пустая / whitespace | Нет изображения `Logo`; AC-3 |
| `Logo.Url` указывает на tmdb.org + `IgnoreTmdbImages=true` | Отфильтрован; AC-6 |
| Fallback-путь: полные данные недоступны, берём данные из поиска | Открытый вопрос OQ-1 (см. ниже); дефолтная рекомендация — добавить логотип из `apiItem.Logo.Url` аналогично постеру/фону |
| Season без ProviderId | Поиск пропускается (существующая логика), логотипа нет — поведение не меняется |

## NFR

- Производительность: без дополнительных HTTP-запросов — `logo` приходит в том же ответе `/v1.5/movie/{id}`; кэширование клиента не меняется.
- Надёжность: отсутствие логотипа не должно ломать возврат постера/фона (проверки null, как для Poster/Backdrop).
- Совместимость: Jellyfin 10.11.x (`Jellyfin.Controller`/`Jellyfin.Model` 10.11.5), `IRemoteImageProvider.GetSupportedImages` + `RemoteImageInfo.Type = ImageType.Logo`.

## Out of scope

- Типы изображений кроме `Logo` (`Thumb`, `Banner`, `Disc` и т.д.).
- Загрузка/кэширование изображений самим плагином — используется стандартный `GetImageResponse`.
- Логотипы сеток (`networks.logo`) и watchability (`watchability.items.logo`) — другие сущности.
- Изменение приоритетов/порядка провайдеров (`Order`).

## Зависимости

- Нет новых внешних зависимостей; изменение локально в `PoiskKinoImageProvider.cs` + тесты.
- DevOps impact: нет (проверено — см. status.md).

## Открытые вопросы

- **OQ-1 (неблокирующий)**: Добавлять ли логотип также в fallback-ветке «только данные из поиска» (когда `GetMovieByIdAsync` недоступен)? API отдаёт `logo` в поиске, симметрия с постером/фоном подсказывает «да»; объём +~10 строк и один тест. Рекомендация Аналитика: **включить в scope**. Решение можно принять на `analysis-review` без отдельного цикла.
- **OQ-2 (информационный)**: Нужна ли дополнительная защитная проверка `ImageUrlHelper.ShouldFilterUrl(logoUrl)` при добавлении (в дополнение к пост-фильтру)? Дублирование, но явное. Рекомендация: следовать решению Архитектора, функционально эквивалентно.

Блокирующих вопросов для Стейхолдера нет: «что» и «зачем» ясны, точка расширения подтверждена.

## Решения

- Out-of-scope пункт брифа про поиск закрыт фактом: `/v1.5/movie/search` не имеет `selectFields`, `logo` входит в фиксированную схему ответа `SearchMovieDtoV1_4`. Условие исключения логотипов из поиска не выполнено.
- Механизм TMDB-фильтрации для логотипов — существующий пост-фильтр в `GetImages` (не прямой вызов `ShouldFilterUrl`, как было сформулировано в брифе).
- Тестовые данные менять почти не нужно: `FullMovieDtoJson` уже содержит валидный `logo.url`.

## Рекомендация Аналитика

- **`continue`**: фича маленькая, низкорисковая, все гипотезы подтверждены, точка расширения Jellyfin 10.11.x доступна.
- Что показать Стейхолдеру на `analysis-review`: данный анализ; единственное содержательное решение — OQ-1 (логотип в fallback-ветке поиска, рекомендация «да»). После решения Стейхолдера — передача Архитектору через Оркестратора.
