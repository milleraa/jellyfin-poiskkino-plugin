# Analysis — `eu-api-endpoint`

Дата: 2026-11-27. Автор: Аналитик. Источники: код плагина (`PoiskKinoMetadataPlugin/`), снимок спеки `api-docs/documentation.yaml` (servers, строка 4731), исходники Jellyfin `master` ([`BasePluginOfT.cs`](https://github.com/jellyfin/jellyfin/blob/master/MediaBrowser.Common/Plugins/BasePluginOfT.cs), [`BasePluginConfiguration.cs`](https://github.com/jellyfin/jellyfin/blob/master/MediaBrowser.Model/Plugins/BasePluginConfiguration.cs), [`MyXmlSerializer.cs`](https://github.com/jellyfin/jellyfin/blob/master/Emby.Server.Implementations/Serialization/MyXmlSerializer.cs)), live-пробы API. Код плагина в рамках анализа не изменялся.

## Резюме

Базовый URL API ПоискКино зашит константой (`PoiskKinoApiClient.cs:15`) и применяется один раз в конструкторе как `HttpClient.BaseAddress` (`:32`); все запросы используют относительные пути. Задача сводится к: (1) новое строковое поле конфигурации с дефолтом `https://api.poiskkino.dev`, (2) нормализация/валидация значения с безопасным fallback на дефолт, (3) применение значения при построении запросов вместо константы, (4) поле и подсказка в `Configuration/configPage.html`, (5) юнит-тесты и обновление документации. Контракт API и тела ответов не меняются — EU-зеркало обслуживает те же методы с тем же токеном.

Ключевой технический факт, влияющий на требования: конфигурация читается лениво один раз (`BasePlugin<T>.Configuration`), а `PoiskKinoApiClient` создаётся лениво один раз на экземпляр провайдера (`Lazy<PoiskKinoApiClient>`, напр. `PoiskKinoMovieProvider.cs:25`), поэтому текущая привязка base URL к конструктору означает, что смена значения в UI не подействует на уже созданный клиент. Требование «применяется без перезагрузки» достижимо, потому что остальные настройки (`ApiKey`, `IgnoreTmdbImages`) уже читаются из `Plugin.Instance.Configuration` на каждый запрос (`PoiskKinoMovieProvider.cs:32`, `ImageUrlHelper.cs:29`), — см. AC-7 и вопрос Q2.

## 2. User stories

1. **Как администратор Jellyfin-сервера за пределами РФ**, я хочу указать в настройках плагина зеркало `https://eu-api.poiskkino.dev`, чтобы поиск метаданных и изображений работал без правки кода и пересборки плагина.
2. **Как администратор с сервером в РФ**, я хочу, чтобы после обновления плагина всё продолжило работать на `https://api.poiskkino.dev` без каких-либо действий с моей стороны (дефолт сохраняется, конфигурация не сбрасывается).
3. **Как администратор, который ошибся при вводе URL**, я хочу видеть понятную подсказку в UI и предсказуемое поведение (плагин не падает, запросы идут на дефолтный хост, в логе есть предупреждение), чтобы исправить настройку, а не искать причину «плагин ничего не находит».
4. **Как сопровождающий плагина**, я хочу, чтобы новое зеркало можно было добавить подсказкой в UI/документации без изменения схемы конфигурации и миграций.
5. **Как QA/разработчик**, я хочу, чтобы выбор базового URL был покрыт автотестами (дефолт, кастом, нормализация, невалидное значение, фактический хост в запросе), чтобы регрессия «снова ходим на жёсткий хост» ловилась CI.

## 3. Acceptance criteria

Проверяемые; в скобках — способ проверки.

**AC-1. Поле конфигурации с дефолтом.** `PluginConfiguration` содержит строковое свойство базового URL (`get`/`set`, инициализатор `"https://api.poiskkino.dev"`); XML-конфигурация без этого элемента даёт именно дефолт. *(code review + unit-тест на дефолт пустой конфигурации)*

**AC-2. Дефолт без изменений поведения.** При пустом/отсутствующем значении все запросы уходят на `https://api.poiskkino.dev`, поведение плагина (поиск, метаданные, изображения, сезоны/эпизоды, кэш, лимит 200/сутки, таймаут 120 с) не меняется. *(unit-тесты + диффом подтверждено отсутствие иных изменений)*

**AC-3. Нормализация.** Значение нормализуется детерминированно: обрезка пробелов по краям; пустая строка/пробелы → дефолт; отсутствие схемы → добавляется `https://`; удаляются завершающие `/`; результат приводится к абсолютному URI. *(unit-тесты: таблица кейсов)*

**AC-4. Валидация без падения.** Невалидное значение (не URL, схема не `https`, пустой host) не приводит к исключению при создании клиента или запросе: используется дефолтный хост и пишется `Warning` в лог один раз на клиент (без утечки ключа). *(unit-тесты: `UriFormatException` не вылетает; лог-ассерт)*

**AC-5. Применение во всех запросах.** Все три вызова (`/v1.5/movie/search`, `/v1.5/movie/{id}`, `/v1.5/season`) строятся от сконфигурированного базового URL; жёсткой константы хоста в коде больше нет (константа дефолта допустима только как значение по умолчанию). *(unit-тест: захват `HttpRequestMessage.RequestUri` и проверка `Host`/`Scheme` для кастомного значения; grep на отсутствие хардкода)*

**AC-6. UI.** В `Configuration/configPage.html` есть поле базового URL, которое: загружает сохранённое значение (при отсутствии — подставляет дефолт), сохраняется вместе с остальными настройками, содержит подсказку с обоими известными хостами и пояснением «сервер вне РФ → eu-api.poiskkino.dev» на русском (язык текущей страницы). *(ручная проверка в UI Jellyfin: сохранить → перезагрузить страницу настроек → значение на месте)*

**AC-7. Применение без перезагрузки.** После сохранения нового значения следующий поиск уходит на новый хост без перезапуска Jellyfin. *(smoke: смена значения на `https://eu-api.poiskkino.dev`, диагностический лог фиксирует фактический хост запроса)*
Если Стейхолдер выберет вариант «перезагрузка допустима» (вопрос Q2), AC-7 заменяется на **AC-7′**: в `README.md` явно указано, что смена хоста применяется после перезапуска Jellyfin, и это поведение подтверждено smoke-проверкой.

**AC-8. Персистентность.** Значение переживает перезапуск Jellyfin и сохраняется в существующем XML-файле конфигурации плагина; старые конфигурации (без нового элемента) читаются без ошибок и без сброса `ApiKey`/`IgnoreTmdbImages`. *(smoke: сохранить, перезапустить, проверить UI и файл конфигурации)*

**AC-9. Диагностируемость.** Фактический базовый URL пишется в лог уровня `Information` при создании клиента (и `Warning` при fallback), API-ключ в лог не попадает. *(code review + лог-ассерт)*

**AC-10. Тесты и сборка.** Добавлены unit-тесты на AC-1/AC-3/AC-4/AC-5; полный прогон `dotnet test` зелёный; `dotnet build -c Release` без новых предупреждений (baseline — только CS1591). *(CI/локальный прогон)*

**AC-11. Документация.** `README.md` и `docs/architecture/overview.md` описывают настройку базового URL и оба хоста (сейчас там только `api.poiskkino.dev`: `README.md:57,61,113`, `overview.md:16,37`). *(code review docs)*

**AC-12. Без новых зависимостей и поверхностей.** Не добавляются NuGet-пакеты, env-переменные, секреты, фоновые задачи; сетевой исходящий хост по умолчанию тот же. *(ревью diff, DevOps impact check)*

## 5. Out of scope

- Автоматический выбор зеркала по геолокации/пингу и автоматический failover между `api.` и `eu-api.` (подтверждено, см. OQ-2).
- Прокси, самоподписанные/собственные зеркала как поддерживаемая фича, произвольные HTTP-заголовки, mTLS.
- Per-provider (movie/series/season/image) базовые URL.
- Ретраи, circuit breaker, изменение таймаутов (`Timeout = 120 s` остаётся), изменение кэша и клиентского rate-limit.
- Схема `http://` (только `https`).
- Новые эндпоинты API (`/v1.5/box-office`, `/v1.5/view-option`, `/v1.5/person`) и миграция путей.
- Хосты изображений: URL изображений приходят абсолютными от API (`ImageUrlHelper` работает с доменом `tmdb.org`) — настройка их домена не входит в фичу.

## 8. Ответы на открытые вопросы из brief

### OQ-1. UI: свободное поле URL или выбор из двух предустановленных значений + «другое»

**Аргументы за свободное поле**
- Схема конфигурации не меняется при появлении третьего зеркала: список предустановок в UI пришлось бы расширять релизом плагина, а строковое поле принимает новое значение сразу.
- Нет дополнительной JS-логики «select + другое → показать input»; страница сейчас минимальна и не имеет валидации вообще.
- Совпадает с существующим паттерном (`ApiKey` — свободный input), меньше риска регрессии UI.
- Позволяет администратору указать собственный прокси/шлюз без отдельной фичи (см. R9) — полезно в корпоративных сетях.

**Аргументы за предустановки**
- Меньше опечаток; пользователь выбирает из двух проверенных значений.
- Снижает соблазн ввести произвольный хост (R9).

**Рекомендация: свободное поле с серверной нормализацией и подсказкой.** Опечатки закрываются не UI-ограничением, а AC-3/AC-4 (нормализация, `https`-требование, fallback на дефолт с предупреждением) и текстом-подсказкой с обоими хостами. Дополнительно допустимо (не обязательно) добавить `<datalist>` с двумя значениями — нативная подсказка без ветвления логики и без блокировки ввода. Тип поля — `text` (не `type="url"`, чтобы не блокировать ввод без схемы на уровне браузера; нормализация всё равно серверная).

### OQ-2. Нужен ли автоматический failover на другой хост при сетевой ошибке

**Подтверждаю out of scope.** Аргументы:
- Скрытый fallback меняет географию запросов незаметно для администратора: сервер в РФ, «упавший» на минуту `api.`, начнёт ходить в EU-зеркало — это может быть медленнее или недоступнее, и диагностировать это по логам плагина сложно.
- Удвоение попыток усложняет учёт суточного лимита (200/сутки) и поведение кэша 404/24 ч; семантика лимита между хостами не подтверждена (R3).
- Failover не решает исходную проблему: если `api.` заблокирован из страны, «сетевая ошибка» будет повторяться на каждой попытке, а не один раз.
- В спеке нет требований к консистентности данных между хостами; смешивание ответов двух хостов в одном кэше — дополнительный риск.
- Реализация (таймауты, дизайн «когда переключаться», метрики) несопоставима с ценностью: ручное переключение — одна настройка.

**Рекомендация:** вместо failover — явный выбор хоста + понятная диагностика (AC-9) + запись в README, когда выбирать EU-адрес. Если потребность в автоматике появится, это отдельная фича с отдельным ADR (политика переключения, учёт лимита, ключ кэша с хостом).

### OQ-3. Фича (enhancement) или hotfix

**Подтверждаю классификацию Оркестратора: enhancement-фича.** Аргументы:
- Дефекта/регрессии нет: на дефолтном хосте плагин работает как раньше; отсутствует *возможность* выбрать зеркало.
- Изменение затрагивает схему конфигурации, UI, документацию и требует новых тестов — это профиль фичи, а не ускоренного hotfix-потока.
- Проблема пользователей вне РФ решается их выбором зеркала, а не исправлением ошибки в коде; issue [#8](https://github.com/milleraa/jellyfin-poiskkino-plugin/issues/8) уже помечен `enhancement`.
- Практический эффект: полный поток (Аналитик → Архитектор → Техлид → разработка → QA) с обязательной остановкой `analysis-review` — это корректно для изменения публичной схемы настроек.

### OQ-4. Миграция существующих конфигураций при добавлении нового поля

**Ответ: миграция не требуется; дефолт применяется автоматически.** Evidence (исходники Jellyfin `master`):
- `BasePluginConfiguration` — пустой класс-маркер, никаких версий/миграций в модели нет.
- `BasePlugin<TConfigurationType>.Configuration` лениво вызывает `LoadConfiguration()` → `XmlSerializer.DeserializeFromFile(typeof(TConfigurationType), ConfigurationFilePath)`; файл — `plugins/configurations/<Assembly>.xml` (`ConfigurationFilePath`).
- Десериализация выполняется через `System.Xml.Serialization.XmlSerializer` (`MyXmlSerializer.GetSerializer` → `new XmlSerializer(type)`), который создаёт объект конструктором без параметров: инициализаторы свойств выполняются, а отсутствующие в XML элементы просто не перезаписываются → новое поле получает дефолт из инициализатора в `Configuration.cs`, старые `ApiKey`/`IgnoreTmdbImages` сохраняются.
- Если файл отсутствует или повреждён (исключение десериализации), Jellyfin создаёт дефолтный экземпляр и **перезаписывает** файл (`LoadConfiguration` → `SaveConfiguration`). Это существующее поведение Jellyfin, не связанное с фичей; в наших AC важно лишь то, что новый элемент не может стать причиной исключения (строка — безопасный тип).
- `UpdateConfiguration` сохраняет присланный объект и вызывает `ConfigurationChanged`; плагин на событие не подписан → значение читается из `Configuration` при следующем обращении (см. R1/AC-7).

**Остаточные риски и план smoke-проверки:**
1. R5 — сценарий «старый XML без нового элемента»: вручную положить конфигурацию от предыдущей версии (`ApiKey` + `IgnoreTmdbImages`, без нового поля), запустить Jellyfin, убедиться, что UI показывает дефолтный URL, ключ на месте, поиск работает.
2. Сценарий «сохранил кастомный URL → перезапуск» (AC-8): проверить, что значение в XML и в UI сохранилось.
3. Сценарий «значение с завершающим `/` и без схемы» (AC-3): после сохранения в UI отображается нормализованное значение либо нормализация происходит на сервере при применении (требование к UI — не терять введённое значение до сохранения).

## 9. Вопросы Стейхолдеру

1. **Q1. Допустим ли произвольный хост (свободное поле), или разрешаем только два объявленных?**
   Рекомендация: свободное поле (OQ-1) — оно не создаёт поддержки прокси как фичи, но не блокирует администратора; валидация ограничивает только схему `https` и корректность URL. Если политика требует минимума сетевых поверхностей — выбрать whitelist из двух хостов (тогда UI = select с двумя значениями, а AC-3/AC-4 упрощаются).
2. **Q2. Обязательно ли применение нового URL без перезапуска Jellyfin?**
   Рекомендация: да (AC-7) — иначе администратор сохраняет настройку, видит «Сохранено», а плагин продолжает ходить на старый хост, что читается как баг. Реализуемо без большого рефакторинга: остальные настройки уже читаются из `Plugin.Instance.Configuration` на каждый запрос. Если Стейхолдер предпочитает минимальный дифф — принимаем AC-7′ (перезагрузка допустима) с явной записью в README.
3. **Q3. Нужно ли показывать в UI текущий фактический хост/остаток лимита (`GET /v1.5/token`)?**
   Рекомендация: нет в этой фиче (вне scope), но отметить как возможное продолжение: эндпоинт `/v1.5/token` не списывает лимит и дал бы полезную диагностику «куда ходим» без реального поиска.

Блокирующих вопросов нет: по каждому есть рекомендация, и они не мешают Архитектору начать работу.

## 10. Решения (для Архитектора и Техлида)

- **D-1.** Новое поле — строка `ApiBaseUrl` (имя на усмотрение Архитектора, дефолт `"https://api.poiskkino.dev"`), без enum: значение задаётся свободным текстом (OQ-1).
- **D-2.** Failover не реализуем; выбор хоста — только конфигурацией (OQ-2).
- **D-3.** Тип работы — enhancement-фича, полный поток (OQ-3).
- **D-4.** Отдельный код миграции конфигурации не нужен; достаточно дефолта в инициализаторе + smoke AC-8 (OQ-4).
- **D-5.** Валидация/нормализация — единая точка (один хелпер/метод), используется и в клиенте, и (по возможности) в UI; невалидное значение → дефолт + `Warning`, без исключений (AC-3/AC-4).
- **D-6.** Значение читается из конфигурации плагина, а не из константы; хардкод хоста в запросах запрещён (AC-5).
- **D-7.** AC-7 (применение без перезагрузки) — целевое поведение; если реализация упирается в жизненный цикл провайдеров, Архитектор фиксирует альтернативу AC-7′ и возвращает вопрос Стейхолдеру, а не «молча» выбирает перезагрузку.
- **D-8.** Существующие кэш, лимит запросов, таймаут и обработка ошибок не меняются (AC-2).
