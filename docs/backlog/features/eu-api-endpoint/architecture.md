# Architecture — `eu-api-endpoint`

Дата: 2026-11-27. Автор: Архитектор. Статус: **готово к `tech-decomposition`**.
Входы: [brief.md](brief.md), [analysis.md](analysis.md), [status.md](status.md), [architecture overview](../../../architecture/overview.md), [ADR-0003](../../../architecture/decisions/ADR-0003-configurable-api-base-url.md).
Глобальный обзор: [architecture overview](../../../architecture/overview.md).

## 0. Резюме дизайна

1. Новое поле конфигурации `PluginConfiguration.ApiBaseUrl` (строка, инициализатор = дефолт `https://api.poiskkino.dev`).
2. Единственная точка политики — новый **чистый** хелпер `ApiBaseUrlResolver` (без зависимостей от Jellyfin/HTTP): константа дефолта + детерминированная нормализация/валидация → `ResolvedBaseUrl(Uri, UsedFallback, Reason)`. Никаких исключений наружу.
3. Значение попадает в `PoiskKinoApiClient` **параметром конструктора** (`string? apiBaseUrl = null`), провайдеры передают сырое значение из `Plugin.Instance.Configuration` — как уже делают с `ApiKey`. Клиент один раз резолвит его и ставит `HttpClient.BaseAddress`; на каждый запрос ничего не пересчитывается.
4. Смена значения применяется **после перезапуска Jellyfin** (решение Q2 → AC-7′): base URL — construction-time параметр клиента, а клиент создаётся лениво один раз на провайдер. Это фиксируется отдельным ADR и в `README.md`.
5. `GET /v1.5/token` в UI (Q3) — **вне scope** этой фичи; зафиксировано как будущая фича с обоснованием стоимости (см. §5).
6. Дефолт и все прочие настройки (`ApiKey`, `IgnoreTmdbImages`), таймаут 120 с, кэш, семафор и лимит 200/сутки не меняются; новых пакетов/env/фоновых задач нет.

## 1. Контекст

- Сейчас хост зашит константой и применяется один раз в конструкторе клиента: `PoiskKinoApiClient.cs:15` (`ApiBaseUrl`), `:32` (`_httpClient.BaseAddress = new Uri(ApiBaseUrl)`). Все три запроса используют относительные пути с ведущим `/` (`/v1.5/movie/search`, `/v1.5/movie/{id}`, `/v1.5/season`) — analysis F1, F2.
- Клиент создаётся лениво один раз на провайдер (`Lazy<PoiskKinoApiClient>` в 5 провайдерах), настройки читаются из `Plugin.Instance?.Configuration` на каждый запрос — analysis F3.
- **Уточнение фактуры (проверено Архитектором).** В Jellyfin `master` `BasePlugin<T>.UpdateConfiguration` делает `Configuration = (TConfigurationType)configuration` **до** `SaveConfiguration` и `ConfigurationChanged` ([`BasePluginOfT.cs`](https://github.com/jellyfin/jellyfin/blob/master/MediaBrowser.Common/Plugins/BasePluginOfT.cs)). Значит, конфигурация в памяти обновляется сразу после сохранения в UI — именно поэтому смена `ApiKey` действует «на лету». Значение base URL не действует на лету **не** из-за конфигурации, а потому что клиент захватывает его один раз в конструкторе. Это делает AC-7 технически достижимым (см. D-ARCH-6), но по решению Стейхолдера (Q2) реализуется AC-7′.
- Ограничения фичи: дефолт = текущее поведение; API-ключ не логируется; без новых NuGet-пакетов, env-переменных и фоновых задач; таймаут/кэш/лимит не меняются (analysis §4, AC-12).

## 2. Компоненты и границы

| Компонент | Слой | Изменение | Ответственность |
|-----------|------|-----------|-----------------|
| `PluginConfiguration` (`Configuration.cs`) | модель конфигурации | + свойство `string ApiBaseUrl` с инициализатором `ApiBaseUrlResolver.DefaultBaseUrl` | хранение выбранного администратором значения; сериализуется в существующий XML Jellyfin |
| **`ApiBaseUrlResolver`** (новый, `internal static`, корень проекта) | политика (чистая функция) | новый файл: `DefaultBaseUrl`, `ResolvedBaseUrl` (record struct), `Resolve(string?)` | что считается валидным базовым URL и во что он нормализуется; без Jellyfin, без HTTP, без логгера → тестируется без моков |
| `PoiskKinoApiClient` | инфраструктурный адаптер (HTTP) | + параметр конструктора `string? apiBaseUrl = null`; base URL берётся не из константы, а из резолвера; + `Information`/`Warning` в лог | применение значения к `HttpClient.BaseAddress`, диагностика фактического хоста |
| `PoiskKino{Movie,Series,Season,Episode,Image}Provider` (×5) | приложение/адаптеры Jellyfin | + `private string ApiBaseUrl => Plugin.Instance?.Configuration?.ApiBaseUrl ?? string.Empty;` и передача в конструктор клиента | чтение конфигурации по существующему паттерну `ApiKey`; никакой нормализации/валидации |
| `Configuration/configPage.html` | UI | + поле «Базовый URL API» + подсказка со двумя хостами (опционально `<datalist>`) | ввод и сохранение значения «как ввёл админ» |
| `README.md`, `docs/architecture/overview.md` | документация | описание настройки, оба хоста, «смена применяется после перезапуска» | AC-7′, AC-11 |

Границы (по [principles.md](../../../architecture/principles.md)):

- **Политика** (что валидно, как нормализовать) — в чистом `ApiBaseUrlResolver`; зависимостей внутрь нет, ничего не знает про Jellyfin, `HttpClient` и `Plugin.Instance`.
- **Транспорт** (как значение применяется к запросам) — в `PoiskKinoApiClient`, который и раньше был единственным местом работы с `HttpClient` (ADR-0001: клиент — транспортный адаптер без бизнес-правил; здесь он получает ещё и «техническую» настройку адреса).
- **Доступ к конфигурации** — только на краю, в провайдерах, ровно как `ApiKey`/`IgnoreTmdbImages`. Клиент не обращается к `Plugin.Instance` (не тянем статический синглтон вглубь).
- Новых DI-регистраций нет: провайдеры инстанцируются механизмом плагинов Jellyfin, клиент создаётся вручную через `IHttpClientFactory.CreateClient()` (безымянный клиент).

```text
Configuration/configPage.html ──(updatePluginConfiguration)──> PluginConfiguration.ApiBaseUrl
                                                                      │ (сырое значение)
                                       providers ×5 (ApiBaseUrl property, как ApiKey)
                                                                      │ ctor(string? apiBaseUrl)
                                          PoiskKinoApiClient ──> ApiBaseUrlResolver.Resolve()
                                                                      │ Uri или дефолт
                                              HttpClient.BaseAddress (+ Information/Warning в лог)
                                                                      │ относительные пути /v1.5/…
                                                              HTTPS → api.|eu-api.poiskkino.dev
```

## 3. Потоки данных

**3.1. Первый запрос провайдера (happy path).**

1. Jellyfin вызывает, например, `PoiskKinoMovieProvider.GetSearchResults`.
2. `ApiClient` (`Lazy.Value`) → `new PoiskKinoApiClient(httpClientFactory, logger, ApiBaseUrl)`; `ApiBaseUrl` читается из `Plugin.Instance.Configuration` **в момент первого обращения**, а не при загрузке плагина.
3. Клиент вызывает `ApiBaseUrlResolver.Resolve(raw)`; при валидном значении получает `Uri`, ставит `_httpClient.BaseAddress`, пишет `Information` «фактический базовый URL».
4. `SendAsync` с относительным путём `/v1.5/...` → `HttpClient` сам склеивает с `BaseAddress`. Таймаут, `User-Agent`, `X-API-KEY`, кэш и семафор — без изменений.

**3.2. Невалидное значение (AC-4).**

`Resolve` не бросает исключений: возвращает `UsedFallback = true`, `Reason`; клиент ставит дефолтный `BaseAddress` и пишет один `Warning` (сырое значение в логе обрезается, ключ не логируется — у резолвера его просто нет). Поиск продолжает работать на дефолтном хосте; администратор видит предупреждение и подсказку в UI.

**3.3. Сохранение настройки.**

`configPage.html` → `ApiClient.updatePluginConfiguration` → Jellyfin обновляет конфигурацию **в памяти** и файл `plugins/configurations/PoiskKinoMetadataPlugin.xml`. Уже созданные клиенты (до 5 экземпляров, по одному на провайдер) продолжают работать со своим `BaseAddress`; новый хост применяется после перезапуска Jellyfin (AC-7′). Если первый запрос провайдера ещё не выполнялся, значение подхватится без перезапуска — это допустимое следствие ленивой инициализации, документация формулируется как «применяется после перезапуска» (гарантия), без обещания «на лету».

**3.4. Старая XML-конфигурация.**

Отсутствующий элемент `<ApiBaseUrl>` не перезаписывает инициализатор → дефолт (analysis OQ-4, F6/F7/AC-8). Миграции нет.

## 4. Принятые решения

### D-ARCH-1. Единственная точка нормализации/валидации — чистый хелпер `ApiBaseUrlResolver`

```csharp
internal readonly record struct ResolvedBaseUrl(Uri BaseAddress, bool UsedFallback, string? FallbackReason);

internal static class ApiBaseUrlResolver
{
    public const string DefaultBaseUrl = "https://api.poiskkino.dev";
    public static ResolvedBaseUrl Resolve(string? rawValue);
}
```

Правила `Resolve` (детерминированные, без исключений):

| # | Вход | Результат |
|---|------|-----------|
| 1 | `null`, пусто, пробелы | дефолт, `UsedFallback = false` (значение не задано — это не ошибка) |
| 2 | пробелы по краям | обрезаются |
| 3 | нет схемы (`://`) | подставляется `https://` (AC-3) |
| 4 | схема не `https` (`http`, `ftp`, `file`, …) | дефолт + `Warning` (analysis §5: только https) |
| 5 | пустой host, не парсится как абсолютный `Uri` | дефолт + `Warning` (AC-4) |
| 6 | есть `userinfo`, `query`, `fragment` | дефолт + `Warning` (не имеет смысла как base address) |
| 7 | непустой путь (кроме `/`) | дефолт + `Warning` — см. D-ARCH-3 |
| 8 | завершающие `/` | удаляются → `https://host[:port]` |
| 9 | явный порт | сохраняется (явный выбор администратора) |
| 10 | регистр/IDN | нормализует сам `Uri` (host в нижнем регистре, punycode) |

Почему отдельный класс, а не приватный метод в клиенте: политика тестируется таблицей кейсов без моков HTTP/логгера, переиспользуется в UI-валидации при желании и не засоряет транспортный адаптер. Стиль совпадает с существующими чистыми хелперами (`SearchYearFilter`, `ImageUrlHelper`), `InternalsVisibleTo` уже настроен (analysis F12/F13).

Отвергнуто: нормализация в `Plugin.UpdateConfiguration` (меняет поведение lifecycle-хука Jellyfin и переписывает конфигурацию существующих пользователей «молча»); нормализация в JS-странице (дублирование правил в двух языках).

### D-ARCH-2. Точка чтения конфигурации — провайдеры, точка применения — конструктор клиента

Провайдер получает свойство `ApiBaseUrl` ровно по образцу `ApiKey` (5 мест, по одной строке) и передаёт **сырое** значение в новый необязательный параметр конструктора:

```csharp
public PoiskKinoApiClient(IHttpClientFactory httpClientFactory, ILogger<PoiskKinoApiClient> logger, string? apiBaseUrl = null)
```

Обоснование:

- Клиент не зависит от статического `Plugin.Instance` (тестируемость, DIP): значение приходит как параметр, дефолт `null` = дефолтный хост.
- Необязательный параметр сохраняет совместимость: существующие тесты (`new PoiskKinoApiClient(factory, logger)`) и код с двумя аргументами продолжают компилироваться, а поведение по умолчанию совпадает с прежним (тесты и так задают `BaseAddress = api.poiskkino.dev`).
- Резолв и логирование в одном месте — не дублируются на 5 провайдеров.

Отвергнуто: передавать `Uri` из провайдера (нормализация и логирование размазываются по 5 классам); читать `Plugin.Instance` внутри клиента (скрытая зависимость от синглтона, сложнее тесты).

### D-ARCH-3. `HttpClient.BaseAddress` остаётся механизмом склейки; базовый URL — только корневой путь

Все три запроса — относительные URI с ведущим `/`. По правилам `System.Uri` такой путь **заменяет** путь базового адреса, то есть base URL вида `https://proxy.corp/poiskkino` молча потерял бы `/poiskkino`. Чтобы не получить «тихую» поломку (риск R4), нормализация **отвергает** непустой путь и уходит на дефолт с `Warning` (D-ARCH-1, правило 7).

Альтернатива «поддержать подпуть» (base URL с завершающим `/` + относительные пути без ведущего `/` + правка трёх строк URL + тесты) отвергнута: прокси/шлюзы как поддерживаемая фича — out of scope (analysis §5, R9), а объём и риск регрессии несоразмерны. Зафиксировано как возможная будущая фича.

### D-ARCH-4. Нормализованное значение не записывается обратно в конфигурацию

В XML и в UI остаётся то, что ввёл администратор; нормализация применяется при создании клиента. Причины: не пишем конфигурацию вне `UpdateConfiguration`; не дублируем правила в JS; фактическое значение видно в логе (`Information`, AC-9).

Следствие, которое нужно принять осознанно: `ApiBaseUrl = "EU-api.poiskkino.dev/"` в файле останется как есть, а работать будет `https://eu-api.poiskkino.dev`. Если Стейхолдер захочет канонизацию в файле/UI — это правка требований, не «тихий» рефакторинг.

### D-ARCH-5. Логирование (AC-9) без риска утечки ключа

- `Information` один раз на создание клиента: `PoiskKino API base URL: {BaseUrl}`.
- `Warning` один раз на создание клиента при fallback: `Invalid API base URL '{Raw}' (обрезано до 200 символов), falling back to '{Default}': {Reason}`.
- Клиентов до 5 (по одному на провайдер) → максимум 5 пар строк на процесс Jellyfin, не на запрос (NFR «без спама»).
- Резолвер не получает и не логирует `ApiKey`; заголовки не логируются.

### D-ARCH-6. Смена базового URL применяется после перезапуска (AC-7′), но AC-7 остаётся достижимым

По решению Стейхолдера (Q2) реализуется AC-7′: «construction-time» значение + явная запись в `README.md`. AC-7 (live-переключение) не реализуется.

Честная оценка альтернативы (для будущей фичи, не сейчас): Jellyfin обновляет конфигурацию в памяти сразу (§1), поэтому live-вариант возможен без перезапуска — но требует (а) строить абсолютные URI на каждый запрос (`new Uri(baseUri, relative)`) вместо `BaseAddress`, (б) хранить/обновлять закэшированный резолв потокобезопасно, (в) включать хост в ключ кэша (R7), иначе 24-часовые записи прошлого хоста будут отдаваться с нового. Это отдельный объём и отдельный ADR-инкремент; в текущей фиче не нужен, так как Стейхолдер принял перезапуск.

### D-ARCH-7. `IHttpClientFactory` используется как раньше (безымянный клиент)

`CreateClient()` возвращает новый экземпляр `HttpClient` на каждый вызов, `BaseAddress` ставится на этот экземпляр → разделяемого изменяемого состояния нет, пул handler'ов не привязан к хосту (после перезапуска соединения к новому хосту устанавливаются штатно). Именованный клиент + `ConfigureHttpClient` отвергнут: в плагине нет DI-регистрации провайдеров, конфигурация всё равно читалась бы один раз на старте (те же restart-семантики), а плумбинг вырос бы.

### D-ARCH-8. Ничего не меняется в таймауте, кэше, лимите, обработке ошибок

`Timeout = 120 s`, `ConcurrentDictionary`-кэш (24 ч / 1 ч для 404), `SemaphoreSlim(1,1)`, обработка 401/403/429/404 и `TaskCanceledException`/`HttpRequestException` остаются как есть (AC-2, AC-12, D-8).

## 5. Решение по Q3 (`GET /v1.5/token` в UI) — вне scope

**Решение: не включать в эту фичу.** Оценка стоимости (замерено 2026-11-27):

- CORS не является блокером: `OPTIONS https://eu-api.poiskkino.dev/v1.5/token` с `Origin` отвечает `204`, `access-control-allow-origin: *`, `access-control-allow-headers: x-api-key`. То есть браузерная проба технически возможна — и именно поэтому решение нельзя принимать «по инерции», оно требует отдельных аргументов.
- **Главный аргумент против:** браузерная проба проверяет сетевой путь **браузера администратора**, а не Jellyfin-сервера. Зеркало выбирают как раз из-за ограничений на стороне сервера — диагностика будет показывать «EU доступен», когда сервер до него не доходит (или наоборот). Такая диагностика вреднее её отсутствия.
- Корректная диагностика требует серверного эндпоинта в плагине (новый HTTP-контроллер плагина, авторизация «только админ», обработка ошибок, новые состояния UI). В плагине сейчас нет ни одного контроллера — это новая поверхность, а не «дёшево» (AC-12 запрещает новые поверхности).
- Дополнительно: ключ уходил бы в запрос из браузера на сторонний хост; на неаутентифицированный `401` API отдаёт отдельный бакет (`x-ratelimit-limit: 5`), то есть частые пробы из UI попадают под лимит анонимных запросов; проверить сценарий в CI нельзя — реального ключа нет (R2), тесты были бы только на моках.
- Ценность дублируется: «куда ходим» уже отвечает `Information`-лог фактического base URL (D-ARCH-5), а остаток лимита администратор смотрит запросом к `/v1.5/token` вручную.

**Что зафиксировать на будущее (отдельная фича, не задача этой):** серверная диагностика «проверить подключение» — эндпоинт плагина, который из процесса Jellyfin делает `GET {base}/v1.5/token` с сохранённым ключом и возвращает в UI хост, код ответа и остаток лимита. Требует решения по новой HTTP-поверхности плагина и по тестируемости без ключа.

## 6. Влияние на существующий код и тесты

| Объект | Влияние |
|--------|---------|
| `PoiskKinoApiClient` | новый необязательный параметр `apiBaseUrl = null`; удаляется `const ApiBaseUrl` (дефолт переезжает в резолвер); + резолв и логирование в конструкторе |
| 5 провайдеров | по одной строке `ApiBaseUrl =>` и по одному аргументу в `new PoiskKinoApiClient(...)`; бизнес-логика не затрагивается |
| `PluginConfiguration` | одно свойство; имя `ApiBaseUrl` становится частью XML-схемы конфигурации (переименование позже = миграция) |
| Существующие тесты | совместимы без правок: 2-аргументный конструктор → дефолтный хост = тот же `https://api.poiskkino.dev`, что уже стоит в фикстурах (F12). Новые тесты передают base URL явно |
| Новые тесты (AC-1/3/4/5) | таблица кейсов резолвера (нормализация/fallback) — без моков; тест клиента: кастомный `apiBaseUrl` → захваченный `HttpRequestMessage.RequestUri.Host/Scheme`; тест дефолта для пустой конфигурации; лог-ассерты `Information`/`Warning` |

## 8. Риски

| # | Риск | Оценка | Митигация |
|---|------|--------|-----------|
| A1 | Значение применяется не мгновенно и не одновременно: 5 клиентов создаются лениво, поэтому без перезапуска возможен кратковременный «смешанный» набор хостов | Средний (осознанно принят с AC-7′) | README + `Information`-лог фактического хоста; формулировка «применяется после перезапуска» |
| A2 | Регресс «снова жёсткий хост» при будущих правках | Средний | AC-5: `grep`-проверка + тест с кастомным base URL, захватывающий `RequestUri.Host` |
| A3 | Ключ кэша не содержит хост (analysis R7) | Низкий при restart-семантике | Инвариант зафиксирован в ADR-0003; при будущем live-переключении хост обязан попасть в ключ кэша |
| A4 | Базовый URL с подпутём (`https://proxy.corp/poiskkino`) молча не сработал бы | Средний | D-ARCH-3: явный отказ + `Warning` с причиной; в README сказано, что путь не поддерживается |
| A5 | Расширение поверхности для произвольных хостов (R9) | Низкий | Свободное поле — решение Стейхолдера (Q1); в README не рекламируем, UI-подсказка ограничена известными хостами |
| A6 | Утечка `ApiKey` в логи через новую диагностику | Низкий | D-ARCH-5: резолвер не имеет доступа к ключу; логируем только URL и причину |
| A7 | E2E-проверка EU-зеркала без реального ключа невозможна (analysis R2) | Средний | Unit-тесты на фактический `RequestUri` + пробы `401`/preflight; ручной smoke администратора после релиза фиксируется в `qa.md` |
| A8 | Имя `ApiBaseUrl` становится частью XML-схемы; переименование позже = миграция | Низкий | Зафиксировано; имя выбрано окончательно (`ApiBaseUrl`) |

## 9. Уточнения к требованиям (не блокирующие)

Зафиксировано Архитектором, повторный проход Аналитика не требуется — но Оркестратору стоит знать:

1. **AC-3 не описывает путь/порт/userinfo/query.** Принято: порт разрешён, `userinfo`/`query`/`fragment`/непустой путь → fallback + `Warning` (D-ARCH-1, D-ARCH-3). Если политика должна быть иной — правка AC-3.
2. **AC-3/AC-6 не говорят, канонизируется ли сохранённое значение.** Принято: нет, в конфигурации и UI остаётся ввод администратора, нормализация применяется при создании клиента (D-ARCH-4).
3. **AC-9 «один раз на клиент»** уточнено: клиентов до 5 (по одному на провайдер), лог — при создании клиента, не при изменении конфигурации. Отдельная запись «настройка изменена, требуется перезапуск» в `UpdateConfiguration` — необязательное улучшение, в scope не включаем (не требуется AC).

## 10. Что передать Техлиду (кандидаты на декомпозицию)

1. `ApiBaseUrlResolver` + `PluginConfiguration.ApiBaseUrl` (дефолт) + тесты таблицы нормализации/fallback (AC-1, AC-3, AC-4).
2. `PoiskKinoApiClient`: параметр конструктора, `BaseAddress` из резолвера, логирование (AC-5, AC-9) + тесты на фактический `RequestUri`.
3. Проводка в 5 провайдерах (одна строка + аргумент каждый) (AC-5).
4. `Configuration/configPage.html`: поле, подсказка с двумя хостами, загрузка/сохранение (AC-6).
5. Документация: `README.md` (включая AC-7′), `docs/architecture/overview.md` (AC-11).
6. Проверки на ревью: отсутствие хардкода хоста, отсутствие изменений кэша/таймаута/лимита, отсутствие новых пакетов/env (AC-2, AC-12).
