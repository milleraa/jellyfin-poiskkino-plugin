# Analysis — `api-v1-5-upgrade`

Дата: 2026-08-23. Автор: Аналитик. Источники: код плагина, `api-docs/documentation.yaml`, https://api.poiskkino.dev/llms.txt, live-пробы API.

## Резюме

Плагин использует два deprecated-эндпоинта v1.4 (`movie/search`, `movie/{id}`); третий вызов (`season`) уже на v1.5. В спецификации v1.5 версии этих эндпоинтов **возвращают те же схемы**, что и v1.4 (`MovieDtoV1_4`, `SearchMovieResponseDtoV1_4`) — контракт тела ответа не меняется, меняется только путь. Основной объём работ — замена двух URL в `PoiskKinoApiClient`, обновление комментариев/имён моделей/тестовых фикстур и добавление теста на путь запроса.

## 2. Различия контрактов v1.4 → v1.5

### 2.1 `GET /v1.4/movie/search` (spec:1773) → `GET /v1.5/movie/search` (spec:2472)

| Аспект | v1.4 | v1.5 | Вывод |
|--------|------|------|-------|
| Query-параметры | `page`, `limit` (default 10, max 250), `query` (required) | идентично | без изменений |
| Ответ 200 | `SearchMovieResponseDtoV1_4` | `SearchMovieResponseDtoV1_4` (**та же схема**) | без изменений |
| deprecated | да | нет | мигрируем |

Ответ остаётся постраничным (`docs`/`total`/`limit`/`page`/`pages`) — курсорная пагинация v1.5 на этот эндпоинт **не распространяется**.

### 2.2 `GET /v1.4/movie/{id}` (spec:3) → `GET /v1.5/movie/{id}` (spec:2416)

| Аспект | v1.4 | v1.5 | Вывод |
|--------|------|------|-------|
| Path-параметр | `id` | идентично | без изменений |
| Ответ 200 | `MovieDtoV1_4` | `MovieDtoV1_4` (**та же схема**) | без изменений |
| Ошибки | 400/401/403/404 | идентично; 403 явно документирует лимит demo/free: страницы 1–10, `limit` ≤ 10 | обработка ошибок в клиенте совместима |
| deprecated | да | нет | мигрируем |

### 2.3 Схемы DTO

- `MovieDtoV1_4` (spec:8556) и `SearchMovieDtoV1_4`/`SearchMovieResponseDtoV1_4` (spec:8880/8985) — единственные схемы для обеих версий. Схем `MovieDtoV1_5` / `SearchMovie*V1_5` в спеке **не существует**.
- Существующие модели плагина покрывают схемы полностью (проверено сопоставлением полей): `PoiskKinoSearchResponse` ↔ `SearchMovieResponseDtoV1_4`, `PoiskKinoItem` ↔ `SearchMovieDtoV1_4` (все поля схемы присутствуют), `PoiskKinoMovieDtoV1_4` ↔ `MovieDtoV1_4`.
- Для season (уже мигрирован): ответ — `SeasonCursorDocsResponseDtoV1_5` (курсоры `next`/`prev`, `hasNext`/`hasPrev`; `total` только при `withCount=true`) поверх элементов `SeasonV1_4`. Модель `PoiskKinoSeasonCursorResponse` этому соответствует. Элементы сезона/эпизода в v1.5 тоже описаны схемами `V1_4` (`SeasonV1_4`, `EpisodeV1_4`; поле `date` у эпизода помечено deprecated в пользу `airDate`).

### 2.4 Итог по контракту

Единственное функциональное изменение — **строка URL**. Переименованных/удалённых/добавленных полей и изменений типов в телах ответов нет. Курсорная пагинация и лимит demo/free (10 страниц, `limit` ≤ 10) на используемые паттерны запросов не влияют: поиск всегда `limit=3`, первая страница; `movie/{id}` — одиночный объект; season уже работает через курсор.

## 4. User stories

1. Как пользователь плагина, я хочу, чтобы плагин обращался к актуальным эндпоинтам ПоискКино v1.5, чтобы метаданные продолжали обновляться после отключения v1.4.
2. Как разработчик плагина, я хочу, чтобы тесты проверяли фактический путь запроса, чтобы деградация на deprecated-версию не проходила незамеченной.

## 5. Acceptance criteria

1. В исходниках плагина (`PoiskKinoMetadataPlugin/`) нет ни одного обращения к `/v1.4/*` (проверяется grep'ом по `.cs`); все запросы идут на `/v1.5/*`.
2. `SearchAsync` вызывает `GET /v1.5/movie/search`, `GetMovieByIdAsync` вызывает `GET /v1.5/movie/{id}`; юнит-тест содержит явную проверку путей запроса.
3. Десериализация ответов v1.5 работает без изменения структуры моделей: все существующие юнит-тесты проходят (`dotnet test`) на текущих JSON-фикстурах.
4. Комментарии в моделях и тестовых данных больше не ссылаются на «v1.4» как на целевую версию API (переименование классов — по решению вопроса №1).
5. Логика маппинга провайдеров на поля Jellyfin (название, год, описание, рейтинги, постеры, персоны, сезоны/эпизоды) не изменяется; поведение поиска (limit=3, опциональный year) сохраняется.
6. Сборка решения и полный прогон юнит-тестов успешны без новых предупреждений.

## 6. NFR / ограничения

- Авторизация `X-API-KEY` (без изменений); base URL `https://api.poiskkino.dev` (без изменений).
- Клиентский rate-limit (`MaxRequestsPerDay = 200`, семафор) и кэш 24 ч — без изменений.
- Ограничение тарифа demo/free (курсоры дальше страницы 10 отклоняются) на паттерны использования плагина не влияет (см. §2.4).

## 8. Открытые вопросы (Стейхолдеру)

1. **Именование моделей.** Переименовать ли C#-классы (`PoiskKinoMovieDtoV1_4` → например `PoiskKinoMovieDto`, аналогично комментариям моделей/фикстур) в рамках этой фичи? Рекомендация: да — объём мал (3 файла моделей-комментариев, ~25 использований типа, 2 тест-класса), устраняет путаницу версий.
2. **Недокументированный `year` в поиске.** Спека v1.5 `movie/search` описывает только `page`/`limit`/`query`, но плагин передаёт `year` (и это покрыто тестом). Сохранить текущее поведение (рекомендация — сохранить, риск низкий) или убрать параметр?
3. **Мёртвый код.** Удалить неиспользуемый `Models/PoiskKinoSeasonResponse.cs` попутно? Рекомендация: да.

Бизнес-фактов, требующих придумывания, нет; все три вопроса имеют рекомендацию Аналитика и не блокируют переход к архитектуре.

## 9. Решения

- Контракт тел ответов v1.5 идентичен v1.4 (§2) → миграция выполняется заменой путей без изменения моделей и маппинга.
- Курсорная пагинация v1.5 на `movie/search` не распространяется — отдельная работа по переходу на `GET /v1.5/movie` (фильтры) не требуется и в scope не входит.

## 10. Out of scope

- Переход поиска на универсальный курсорный `GET /v1.5/movie` с фильтрами (`!`, `+`, диапазоны).
- Реализация клиентской курсорной пагинации для новых запросов (плагин всегда берёт первую страницу).
- Изменения кэширования, rate-limit, конфигурации, UI настроек.
- Поддержка прочих доменов API (person, review, image и т.д.) — плагин их не использует.

## 11. Зависимости

- Внешние: доступность эндпоинтов `/v1.5/movie/search`, `/v1.5/movie/{id}` на проде (подтверждено пробой, см. риски).
- Внутренних блокирующих зависимостей нет; DevOps-влияния нет (URL — не секрет, env vars не меняются).
