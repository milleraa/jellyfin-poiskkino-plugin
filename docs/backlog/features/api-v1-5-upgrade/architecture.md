# Architecture — `api-v1-5-upgrade`

Дата: 2026-08-23. Автор: Архитектор. Входы: [analysis.md](analysis.md), `api-docs/documentation.yaml`, решения Стейхолдера (status.md, Changelog от 2026-08-23).

## Резюме

Миграция сводится к замене двух URL в `PoiskKinoApiClient` (`/v1.4/movie/search` → `/v1.5/movie/search`, `/v1.4/movie/{id}` → `/v1.5/movie/{id}`); контракты тел ответов идентичны (analysis.md §2). Дополнительно, по решению Стейхолдера:

- переименование моделей `*V1_4` → нейтральные имена (без версии);
- параметр `year` в поиске: **фильтра `year` в `movie/search` нет ни в v1.4, ни в v1.5** — параметр всегда был недокументированным. Решение — гибрид: сохранить передачу `year` в URL (как сегодня) **и добавить гарантированную локальную фильтрацию результатов по году в провайдерах**. Детали и обоснование — §2 и [ADR-0001](../../../architecture/decisions/ADR-0001-search-year-filter.md);
- удаление мёртвого `Models/PoiskKinoSeasonResponse.cs`.

## 1. Целевая схема вызовов API

Все вызовы плагина после миграции:

| Метод клиента | Эндпоинт | Параметры | Ответ |
|---------------|----------|-----------|-------|
| `SearchAsync(title, year?, apiKey)` | `GET /v1.5/movie/search` | query: `query={title}`, `limit=3`, опционально недокументированный `year={year}`; header `X-API-KEY` | `SearchMovieResponseDtoV1_4` → модель `PoiskKinoSearchResponse` |
| `GetMovieByIdAsync(id, apiKey)` | `GET /v1.5/movie/{id}` | path: `id`; header `X-API-KEY` | `MovieDtoV1_4` → модель `PoiskKinoMovieDto` |
| `GetSeasonAsync(movieId, number, apiKey)` | `GET /v1.5/season?movieId=&number=` | без изменений (уже v1.5) | `SeasonCursorDocsResponseDtoV1_5` → `PoiskKinoSeasonCursorResponse` |

Не меняются: base URL `https://api.poiskkino.dev`, авторизация `X-API-KEY`, обработка ошибок (400/401/403/404/429), кэш 24 ч (404 — 1 ч), семафор и клиентский rate-limit (`MaxRequestsPerDay = 200`).

Курсорная пагинация v1.5 на используемые эндпоинты не влияет: поиск всегда первая страница с `limit=3`, `movie/{id}` — одиночный объект, season уже работает через курсор.

## 2. Решение по параметру `year` (приоритетная задача Стейхолдера)

### Факты

1. **В коде** (`PoiskKinoApiClient.cs:81–85`) `year` передаётся как **query-параметр запроса**: `&year={value}` добавляется к URL поиска, если указан. Это не только локальное поле — параметр реально уходит в HTTP-запрос.
2. **В спеке v1.4** (`documentation.yaml`, `/v1.4/movie/search`, строка ~1773) документированы только `page`, `limit`, `query`. Параметр `year` **не документирован и там**.
3. **В спеке v1.5** (`/v1.5/movie/search`, строка ~2472) — те же `page`/`limit`/`query`, фильтра `year` нет.
4. Существующий тест `SearchAsync_WithYear_IncludesYearInUrl` проверяет только построение URL на стороне плагина — он не доказывает, что сервер применяет фильтр.
5. Поле `year` в элементах ответа есть (`SearchMovieDtoV1_4.year`, модель `PoiskKinoItem.Year`), для сериалов — диапазон `releaseYears`. Локальная фильтрация возможна.
6. Документированный фильтр `year` есть только у универсального `GET /v1.5/movie` (синтаксис `2020`, `!2020`, `2020-2024`, курсорная пагинация).

### Ответ на вопрос Стейхолдера

«Его больше нет?» — его не было и в v1.4 как документированного фильтра; это недокументированный query-параметр, который плагин передавал «в надежде» на серверное поведение. Гарантии, что сервер его применяет, нет (спека молчит, live-проба без ключа ничего не доказывает).

### Решение (ADR-0001): гибрид «сохранить параметр + локальная фильтрация»

Выбран **вариант A с сохранением передачи параметра**:

1. URL продолжает содержать `&year={year}` при наличии года — поведение не деградирует, если сервер его учитывает (как в v1.4).
2. Провайдеры (Movie/Series) дополнительно фильтруют результаты поиска по году **на стороне плагина**:
   - фильм: `item.Year == searchInfo.Year`;
   - сериал: год попадает в `item.ReleaseYears` (`start..end`) либо совпадает с `item.Year`.
   - если после фильтрации список пуст, а до фильтрации был непуст — вернуть неотфильтрованный список и записать debug-log (защита recall'а при расхождениях годов между источниками метаданных);
   - если год не указан (обычный refresh метаданных) — фильтрация не применяется.
3. Фильтрация размещается в провайдерах (слой приложения, рядом с существующим `.Where(r => r.IsSeries != true)`), а не в `ApiClient`: клиент остаётся транспортным адаптером без бизнес-правил (clean architecture, инверсия зависимостей). Кэш не затрагивается — кэшируется сырой ответ API.

Отвергнут вариант B (`GET /v1.5/movie` с фильтрами `name`/`year`): другая семантика (листинг с курсором вместо текстового поиска), другой контракт выдачи, усложнение из-за курсорной пагинации и лимитов demo/free — непропорционально задаче миграции (analysis.md §10 прямо выводит это из scope).

Бизнес-гарантия для Стейхолдера: **год, указанный в «Распознать» Jellyfin, теперь учитывается детерминированно — независимо от поведения сервера**.

Полное обоснование и альтернативы: [ADR-0001](../../../architecture/decisions/ADR-0001-search-year-filter.md).

## 3. Изменения по слоям

### Инфраструктура — `PoiskKinoApiClient`

- Замена URL: строка 81 `/v1.4/movie/search` → `/v1.5/movie/search`; строка 202 `/v1.4/movie/{id}` → `/v1.5/movie/{id}`.
- Возвращаемый тип `GetMovieByIdAsync`: `PoiskKinoMovieDtoV1_4` → `PoiskKinoMovieDto` (переименование).
- Комментарии `<summary>` больше не упоминают v1.4 как целевую версию.
- Остальное (кэш, семафор, ошибки, заголовки) — без изменений.

### Модели (`PoiskKinoMetadataPlugin/Models`)

Переименование классов (Стейхолдер: решение №1 — да):

| Текущее имя | Новое имя |
|-------------|-----------|
| `PoiskKinoMovieDtoV1_4` | `PoiskKinoMovieDto` |
| остальные модели (`PoiskKinoSearchResponse`, `PoiskKinoItem`, `PoiskKinoSeason`, `PoiskKinoEpisode`) | имена без версий уже; убрать упоминания «v1.4» из XML-комментариев |

Удалить мёртвый `Models/PoiskKinoSeasonResponse.cs` (решение №3). JSON-контракты (`JsonPropertyName`) не меняются — десериализация совместима (AC №3 analysis.md).

Примечание для Техлида: схемы API формально называются `*V1_4` даже в спецификации v1.5 — в комментариях моделей допустимо сослаться на схему спеки, но имя C#-класса версии содержать не должно.

### Приложение — провайдеры

- `PoiskKinoMovieProvider`, `PoiskKinoSeriesProvider`, `PoiskKinoImageProvider`: замена типа `PoiskKinoMovieDtoV1_4` → `PoiskKinoMovieDto` в сигнатурах/локальных переменных; логика маппинга на Jellyfin не меняется.
- `PoiskKinoMovieProvider.GetSearchResultsInternal` и аналог в `PoiskKinoSeriesProvider`: добавить локальную фильтрацию по году (§2.3).
- `PoiskKinoEpisodeProvider`, `PoiskKinoSeasonProvider`: не затронуты.

### Тесты

- `PoiskKinoApiClientTests`: переименовать типы; **добавить assertion фактического пути запроса** (`/v1.5/movie/search`, `/v1.5/movie/{id}`) — сейчас путь нигде не проверяется (регрессия на v1.4 прошла бы незамечено). Тест `SearchAsync_WithYear_IncludesYearInUrl` сохраняется (параметр остаётся в URL).
- Новые юнит-тесты локальной фильтрации по году: совпадение по `Year`, попадание в `ReleaseYears` (сериал), fallback при пустом результате, отсутствие года → без фильтрации.
- `TestJsonData.cs`: обновить комментарии («v1.4» → актуальные пути v1.5); содержимое JSON-фикстур валидно без правок.
- `PoiskKinoMovieDtoV1_4Tests` → `PoiskKinoMovieDtoTests`.

## 4. Совместимость и риски

| Риск | Оценка | Митигация |
|------|--------|-----------|
| Живой индекс llms.txt не перечисляет `/v1.5/movie/search` и `/v1.5/movie/{id}` | Низкий: live-проба вернула 401 (auth до роутинга) — маршруты существуют | Smoke-тест с реальным ключом после реализации; план отката ниже |
| Сервер перестал принимать недокументированный `year=` (например, strict-валидация query в v1.5) | Низкий→Средний: неизвестно, как v1.5 обрабатывает неизвестные параметры | Smoke-тест с ключом: запрос с `year=` должен вернуть 200. При отказе — убрать параметр из URL (локальная фильтрация уже гарантирует поведение), это изолированная правка одной строки + один тест |
| Расхождение годов источников → фильтр отсекает правильный результат | Средний по UX | Fallback на неотфильтрованный список при пустом результате + debug-log |
| Переименование типов ломает внешних потребителей | Низкий: плагин — самодостаточная сборка, публичный API вне решения не потребляется | Обычная компиляция + полный прогон тестов |

План отката: миграция — два URL в одном файле; откат = revert коммита (ветка фичи, PR не смешивается с другим функционалом). Если v1.5-маршруты окажутся недоступны на проде — временный revert на v1.4 до их включения (v1.4 продолжает работать на текущий момент).
