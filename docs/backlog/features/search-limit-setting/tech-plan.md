## Решение по A1 (дедупликация `Warning` при невалидном значении)

**Механизм — памятка на уровне экземпляра `PoiskKinoApiClient`.** Резолвер остаётся чистой статической функцией без состояния (по образцу `ApiBaseUrlResolver`, который «ничего не сохраняет»); клиент — единственное место записи `Warning` и уже владеет изменяемым состоянием (`_cache`), поэтому дедупликация живёт там:

- приватное поле «последнее предупреждённое невалидное значение» (`int`, инициализация `int.MinValue`);
- при невалидном значении `Warning` (причина + значение, без утечки API-ключа) пишется только если значение отличается от памятки; памятка обновляется;
- при применении валидного значения памятка сбрасывается (эпизод «исправил и снова сломал» даёт новое предупреждение);
- потокобезопасность: чтение/запись `int` атомарны в .NET; гонка в худшем случае даёт дубль предупреждения — допустимо для лога;
- верхняя граница: ≤1 предупреждение на различное невалидное значение на экземпляр клиента; клиентов три (по одному `Lazy<>` на провайдера) → ≤3 строки на значение за время жизни процесса вместо спама на каждый поиск.

Статическая памятка отвергнута: статическое изменяемое состояние течёт между юнит-тестами и противоречит зафиксированной чистоте резолвера. Дедупликация покрывается юнит-тестом (AC-4, задача 002).
