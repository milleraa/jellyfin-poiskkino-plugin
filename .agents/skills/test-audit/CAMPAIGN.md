# Полная проверка тестов подсистемы

Проверяй все тесты одной подсистемы в рамках одного MR: например, тесты одной области backend или frontend либо общего контракта. Для каждой группы действуют правила из [SKILL.md](SKILL.md): выясняй пользу тестов, сохраняй самостоятельные проверки, обосновывай удаление и проверяй результат.

Ниже — порядок полной проверки, составленный по опыту такой работы. Закончи каждый этап и запиши его результат, прежде чем переходить к следующему.

## 1. Зафиксируй исходное состояние

Выбери конкретный коммит. Запиши, сколько строк занимают тесты и их вспомогательный код в подсистеме. Запусти каждый файл тестов и запиши, какие проходят и какие падают. Падающие тесты веди отдельным списком: они могут указывать на реальные ошибки продукта.

Готово, когда записан результат каждого тестового файла подсистемы.

## 2. Раздели тесты на группы

Сгруппируй тесты по компоненту или контракту, чьё поведение они проверяют, а не по имени файла. Например, у backend могут получиться группы обработчиков запросов, обработки вызовов, хранения данных, HTTP и общих фикстур. У frontend — компонентов, доступа к данным и пользовательских сценариев. Включи тесты подсистемы из общих наборов, ручные сценарии и проверки реального пользовательского потока.

Готово, когда каждый тестовый файл и ручной сценарий подсистемы входит ровно в одну группу.

## 3. Запиши решение по каждому тесту

Если доступно делегирование, поручи каждую группу отдельному агенту для изучения без правок. Иначе разбери группы последовательно и укажи это в отчёте. Он читает все назначенные тесты целиком, в том числе таблицы параметров, а также код проверяемых компонентов, точки входа, вызывающий код, историю и способ запуска тестов. Составь реестр: для каждого теста укажи решение и его основание. Параметризованный тест считай одним тестом, если решение одинаково для всех строк; иначе оцени строки отдельно.

- `R` — **оставить**: назови контракт и возможную ошибку, которую ловит тест. Если тест нужно только перенести в файл с более точным именем, оставь `R` и запиши перенос.
- `F` — **исправить, сохранив проверку**: контракт нужен, но нынешнее условие проверки может дать ложный успех. Например, тест проверяет отсутствие ошибки, хотя проверяемое действие вообще не произошло; или должен убедиться, что отсутствуют все запрещённые элементы, а проходит уже при отсутствии одного.
- `C` — **объединить**: назови конкретный существующий тест или набор, куда перенесёшь нужную проверку. Это может быть соседний параметризованный тест, проверка результата работы компонента или общий набор в другом проекте.
- `D` — **удалить**: назови тест, который продолжит проверять тот же контракт, или объясни, почему самостоятельного контракта здесь нет.

Проверки структуры исходников — состава solution, ссылок, имён типов, строк и фрагментов текста — решай как `D`: они не наблюдают поведение и запрещены в [SKILL.md](SKILL.md#запрет-на-проверки-структуры-исходников).

Оценивай фактические условия проверки, а не имя теста. Тест с именем «закрывает окно» может в действительности проверять, что окно осталось открытым.

Готово, когда у каждого теста есть решение с основанием.

## 4. Проверь повторы между наборами тестов

Реестр отдельных тестов ещё не готовый план правок. Пересмотри его без правок в коде и найди целые наборы, которые повторяют друг друга. Например, несколько наборов проверяют один общий метод через подменённую зависимость, хотя другой набор уже проверяет то же поведение через обычный вход в компонент. Для каждого контракта назови набор тестов, который оставишь. Когда подходит проверка через обычный вход в компонент с подменой сети, предпочитай её проверке внутреннего взаимодействия с подменённой зависимостью. Исправь найденные ошибки реестра.

Готово, когда для каждой группы записано, какие файлы убрать, какой набор сохранить для каждого контракта, какие проверки в него перенести и какой код продукта, созданный только ради тестов, после этого станет ненужным.

## 5. Внеси правки

Обрабатывай группы по очереди. Если несколько групп используют общие вспомогательные файлы тестов, назначь одного ответственного за их изменение и вноси эти правки последовательно. При обработке каждой группы удаляй ставшие ненужными элементы кода продукта: параметры для внедрения зависимостей, методы чтения состояния, экспорты для сброса состояния и лишние обёртки. Если перенёс тесты, обнови места, где репозиторий перечисляет тестовые файлы, и связанные ограничения для числа строк или других показателей. Правила размещения тестов, подтверждённые находками этой проверки, запиши в `AGENTS.md` подсистемы.

Готово, когда правки по всем группам внесены и сохранённые тесты проходят.

## 6. Убедись, что важные проверки не потеряны

Попроси независимых проверяющих сравнить удалённые тесты с сохранёнными: по одному проверяющему на группу связанных компонентов. Они ищут поведение, для которого исчезла единственная проверка, и новые условия, которые не могут выявить ошибку. Если независимый проверяющий недоступен, зафиксируй это и передай проверку вручную; не выдавай самопроверку за независимое ревью. Например, проверка отказа бесполезна, если проверяемый код никогда до неё не доходит.

Для каждого восстановленного контракта временно внеси одну намеренную ошибку в проверяемый компонент и убедись, что сохранённый тест падает. Затем верни исходник в точности к прежнему состоянию.

Готово, когда по каждому найденному пропуску проверка восстановлена либо доказано по исходникам, что она не нужна; каждый восстановленный тест поймал намеренную ошибку.

## 7. Разбери обнаруженные дефекты продукта

Если тест падал до начала работы и остался в сохранённом наборе, рассмотри это как сообщение о возможном дефекте. Исправь его в проверяемом компоненте отдельным коммитом. Проверь реальный пользовательский сценарий дважды: с исправлением он должен проходить, а при временной отмене исправления — снова показывать старую ошибку. Затем верни исправление. Несвязанные находки запиши как отдельные следующие задачи.

Готово, когда для каждого исправленного дефекта показаны падение без исправления и успех с ним в одном и том же сценарии.

## 8. Сверь изменения с целевой веткой и подготовь отчёт

Полная проверка может занять несколько изменений в целевой ветке PR/MR. Сверься с её актуальным состоянием. Обновляй рабочую ветку только по правилам репозитория и по согласованию с владельцем работы; не переписывай историю самостоятельно. Если в целевой ветке изменился файл тестов, удалённый в аудите, перенеси новую полезную проверку в оставленный набор. Убедись, что у каждой новой проверки регрессии из целевой ветки есть место. После согласованного обновления рабочей ветки запусти все тесты подсистемы и повтори проверку реального пользовательского сценария.

Инструменты просмотра большого MR могут показывать неполный список файлов. Решения сопровождающего запиши в материалы MR; не меняй правила проверок, чтобы обойти замечания.

Подготовь [итоговый отчёт](SKILL.md#итоговый-отчёт) и добавь:

- число строк тестов и вспомогательного кода до и после работы; код продукта посчитай отдельно;
- какие группы разобраны, какие наборы удалены и какие сохранены;
- какие пропущенные проверки найдены и как сохранённые тесты поймали намеренные ошибки;
- какие дефекты продукта найдены и как показано их поведение до и после исправления.
